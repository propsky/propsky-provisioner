# Code Review 第二輪（2026-09-11）

第一輪的問題大多已修：raw REPL 改成三段式讀取、`reset()` 不再等回應、token/MAC/RSSI/程式版本/MQTT 驗收與回寫帳本都補上了、FAIL 會寫回帳本、`update_result` 改抓最新一列、`find_by_mac` 會查 xlsx、Ledger 加了鎖、`backup()` 有呼叫、port 重複有擋、連線有重試 3 次、wifi.dat/token.dat 也驗 sha256、config 會存下一個號碼。方向都對。

**但這一輪引入了兩個新的 P0，實機上第一個指令就會掛。**

## P0 — 新引入的問題

### 1. `_read_until` 會把 marker 之後的資料一起吃掉，導致每個 `execute()` 必逾時（`provisioning.py:74-75,112-122`）

pyserial 的 `read(256)` 在 timeout=2 秒內會**等到收滿 256 bytes 或滿 2 秒才返回**。板子的回應（例如 `<stdout>\x04\x04>`，通常遠小於 256 bytes）會在同一個 chunk 一次全部進來。`_read_until(b"\x04")` 檢查到 marker 就把**整個 buffer**回傳——包含第一個 `\x04` 之後的 stderr 段、第二個 `\x04` 和提示字元 `>`：

- 第 74 行的 `[:-1]` 只削掉最後一個字元（`>`），stdout 裡還殘留 `\x04\x04`；
- 更致命的是資料已被讀光，第 75 行讀 stderr 的 `_read_until` 拿到的 timeout 是 `max(0, deadline - now)` ≈ **0**（前一次讀已耗掉整個 2 秒預算），while 迴圈一次都不會跑 → 直接丟「序列埠逾時」。

結果就是**每一次 `execute()` 都固定耗 2 秒然後失敗**，整個流程一步都走不動。

修法：`_read_until` 要在 marker 處切開，marker 之後的 bytes 留在類別內的 buffer 給下一次讀取用（`_read_exact` 也要走同一個 buffer）；讀取時用 `read(self.serial.in_waiting or 1)` 之類的方式避免為了湊滿 256 bytes 空等。

### 2. 韌體日期永遠比對不上 → 無限重燒迴圈（`provisioning.py:185,299-300`）

MicroPython 的 `os.uname().version` 格式是 `v1.29.0 on 2026-08-24`——日期**帶連字號**。`_read_firmware` 用 `20\d{6}`（連續 8 位數字）去抓，永遠抓不到 → 回傳值只有 `"1.29.0"` → 第 185 行 `firmware.date("20260824") not in "1.29.0"` 恆為 True → **每片板子（包括剛燒完正確韌體的）都判定不符、重燒**。重燒完丟「請重新按開始」，人員重按後又進同一個判斷、又重燒——無限迴圈，永遠到不了步驟 3。

修法：改抓 `(20\d\d)-?(\d\d)-?(\d\d)` 再正規化成 `YYYYMMDD` 比對。

這兩條說明目前的修改只有 2 個原有測試覆蓋，協定層完全沒測。`RawReplClient` 用假的 serial 物件（模擬「一個 chunk 進來整包資料」的行為）很容易測，強烈建議修這輪時一起補。

## P1 — 上輪遺留未修

### 3. 畫面上改「起始編號」對配號無效（`ui.py:220,376-381,466-468`）

`self.next_card` 只在 `__init__` 設一次。使用者在欄位改成 `G100` 後，`_save_settings` 只寫 config，`next_card` 還是舊值 → 這個 session 配號仍從舊號開始。要在 `editingFinished`（且 `cards_used == 0` 或經確認）時同步更新 `self.next_card`。另外規格第 4 節的「檢查帳本內 MAC、token、小卡編號重複」啟動檢查仍未實作。

## P2 — 殘留的規格偏差

- **重燒韌體後仍中斷流程**（`provisioning.py:188`）：規格要求重燒後自動回步驟 1 續跑，現在還是丟錯要人重按。且因為 #2，現在這條會變成無限迴圈的一環。
- **進不了 REPL 不會自動重燒韌體**（`provisioning.py:60`）：重試 3 次失敗直接放棄；規格第 8 節說「進不了 REPL → 自動重燒」。
- **`find_by_mac` 的 xlsx 讀取在鎖外**（`ledger.py:46-57`）：另一個 worker 正在 `sync_xlsx` 存檔時讀，可能讀到寫到一半的檔案。把 xlsx fallback 也包進 `self._lock`。
- **`retry_boot` 不驗 token/MAC**（`provisioning.py:273-281`）：重開機驗收只看 Wi-Fi OK/Traceback，但 `_on_finished` 照樣顯示「✓ token 一致 ✓ MAC 一致」（`ui.py:406`）——重開機路徑的綠勾仍是假的。可以用 MAC 從帳本撈預期值來驗。
- **「識別」只改文字、不閃燈**（`ui.py:162-163`）：訊息說「請確認 TX 指示燈」但程式沒開 port 送資料，燈不會閃。應短暫開 port 寫幾輪 bytes。
- **PyInstaller 打包後 esptool 會壞**（`provisioning.py:140-141`）：`sys.executable -m esptool` 在凍結後指向 provision.exe 自己。打包前必修。
- **`append_csv` 的 PermissionError 未接住**（`provisioning.py:243`）：CSV 被 Excel 開著時整片直接 FAIL。
- **RSSI 低於 -75 dBm 沒有顯示警告**（規格第 6 節，只記錄了數值）。

## P3 — 小問題

- 「今日紀錄」仍是全檔統計，不分日期（`ui.py:451-462`）。
- 清檔用 `os.remove` 碰到目錄（如 `lib/`）會炸成 ProvisionError（`provisioning.py:200-202`）。
- payload 內含 boot.py/wifi.dat/token.dat 時規格要「提示」，目前是靜默略過（`provisioning.py:287-288`）。
- MQTT 判定在 60 秒開機窗內做，規格是「人工確認期間背景繼續讀」——板子較慢連上 MQTT 就會被記「未確認」。

## 結論

修復優先順序：**#1 → #2**（不修這兩個，工具在實機上零功能）→ #3 → P2 裡的 retry_boot 假綠勾與鎖的問題。#1 修好後強烈建議立刻用假 serial 補 `RawReplClient` 的單元測試再繼續。
